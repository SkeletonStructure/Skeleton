# SkeletonStructure v0.2.0

Release date: 2026-11-27

`v0.2.0` is the first post-`v0.1.0` release. It keeps the `v0.1.0` compatibility baseline intact and adds the M11 security/operational hardening and M12 application-runtime work that were merged after that tag. It is a usable foundation release, **not** a claim that the project is production-ready beyond the tested scope.

The historical `v0.1.0` record remains in [`./v0.1.0.md`](./v0.1.0.md); changes in this release are listed in [`../../CHANGELOG.md`](../../CHANGELOG.md).

## Included

### M11 — security and operational hardening

- Provider-independent shared rate limiting: core `RateLimitStoreProvider`, a default in-memory store, an optional application-injected ioredis-compatible client, explicit `security.rateLimit.store`, and fail-closed enforcement before authorization/CSRF hooks. No Redis dependency or default service is added.
- Persistent append-only audit events: the core-owned `core_audit_events` table and triggers, a validated core sink, transaction-aware auth/users events, and audit-specific readiness failures.
- Dependency-free structured logging: JSON/pretty formats, configured redaction, request correlation, and stable event names. Raw bodies, URLs, headers, and credentials are not logged.
- Explicit lifecycle and bounded graceful shutdown: readiness drains before resources close, HTTP/providers/database close once, and the original termination signal is re-raised.
- Regression coverage for redaction, level filtering, request correlation, limiter and audit failures, readiness reasons, lifecycle transitions, and shutdown timeouts.
- Governance evidence and repair of eight pre-existing Biome formatting errors; no repository setting was changed and no CodeQL alert was dismissed.

### M12 — reusable application runtime and starter

- Shared `startApplication()` and `runApplicationMigrations()` helpers in `@skeletonstructure/app-composition`; root and e-commerce demo scripts now delegate to them without CLI behavior changes.
- An additive, opt-in migration readiness check in core. Applications that explicitly pass migration folders fail readiness with only `MIGRATIONS_PENDING` when a recorded hash is missing or state cannot be read. SQL, migration paths, and database errors are not exposed.
- `templates/basic-app`, a minimal workspace starter with its own config, scripts, README, and integration test. It composes the shared M8 module graph and adds no shared domain code.
- ADR 0013 and aligned API, database, security, QA, architecture, and engineering-skill documentation.

Accepted ADRs 0008–0013 record the decisions. Historical ADRs were not rewritten.

## Compatibility and migration notes

- **Public API:** No route, operation, permission, required parameter/body field, or response-code change. The `v0.1.0` operations baseline and empty allowlist remain authoritative. The only contract-metadata change is `info.version`, which moves from `0.1.0` to `0.2.0`.
- **SDK:** Generated operation aliases and client behavior are unchanged; the SDK remains private, source/workspace distributed, and not published to npm.
- **Config:** No breaking config change and no change to existing defaults. M11 adds the optional `security.rateLimit.store`; M12 adds no config field. Redis still requires an application-injected client.
- **Database:** The `v0.1.0` migration files remain byte-for-byte pinned. `v0.2.0` appends one core migration, `0001_supreme_blazing_skull.sql`, for the audit table. Fresh migration and no-op re-run smoke checks passed.
- **Startup:** Root and demo startup retain their prior readiness behavior. Only applications that opt into migration folders get the new preflight. Startup never auto-migrates; running `pnpm db:migrate` remains an explicit operator action.
- **Upgrade expectation:** Existing `v0.1.0` databases must run `pnpm db:migrate` to append the core audit migration before deploying `v0.2.0`. Take a backup first. A live upgrade of an existing production database was not performed during release preparation; verify against a copy of your own database.
- **Readiness limitation:** Migration readiness proves that expected Drizzle hashes are recorded, not that schema semantics are correct. Applications must list every applied migration folder; custom runners must write `drizzle.__drizzle_migrations` to be recognized.

## Security and limitations

The `v0.1.0` security checklist and owner sign-off remain a historical record. M11 and M12 do not carry a new independent security review or a second-maintainer sign-off. All five CodeQL alerts were observed as `fixed`; none was dismissed. The three moderate advisories are `esbuild` (`GHSA-67mh-4wv8-2f99`), `glob` (`GHSA-3g3m-2fjr-6pw4`), and `minimatch` (`GHSA-g3hv-75wg-m249`), all in development/test dependency chains.

Still absent or deferred:

- M9b restaurant demonstration, payments, refunds, cancellations, inventory release, and guest checkout.
- MFA, OAuth, CAPTCHA, per-account limits, real SMTP/HTTP email, file uploads, webhooks, and multi-tenancy.
- Production deployment manifests, bundled Redis/TLS setup, metrics/tracing, and a documented fork-upgrade procedure.
- A second write maintainer with independent review authority; branch protection still requires zero status checks and zero approvals.

Operators remain responsible for TLS, secret management, least-privilege database credentials, backups, dependency updates, monitoring, and deployment hardening. Report suspected vulnerabilities privately as described in [`../../SECURITY.md`](../../SECURITY.md).
