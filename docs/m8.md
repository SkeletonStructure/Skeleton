# M8 — First business modules

M8 adds four optional business packages on top of the M1–M7 core: `catalog`, `products`, `inventory`, and `orders`. The core remains generic; all domain tables, routes, permissions, and use cases live in the owning module packages. A non-domain `app-composition` package wires the modules together at startup.

## Module graph and ports

| Module      | Requires                   | Provides           | Consumes                                                               |
| ----------- | -------------------------- | ------------------ | ---------------------------------------------------------------------- |
| `users`     | —                          | —                  | —                                                                      |
| `auth`      | `users`                    | `buyer-context@1`  | —                                                                      |
| `catalog`   | —                          | —                  | —                                                                      |
| `products`  | `catalog`                  | `price-resolver@1` | —                                                                      |
| `inventory` | `catalog`                  | `inventory@1`      | —                                                                      |
| `orders`    | `auth`, `users`, `catalog` | —                  | `buyer-context@1`, optional `price-resolver@1`, optional `inventory@1` |

`catalog` publishes the generic `PriceResolverPort`, `InventoryPort`, `ItemSnapshot`, and `StockReservationItem` contracts without importing any extension. `products` and `inventory` are ordinary catalog extensions keyed by `catalogItemId`. `orders` imports only those contracts; it never imports `products`, `inventory`, `auth`, or `users` implementations.

`products` and `inventory` declare hard `requires: ['catalog']` and deliberately do not use `enhances`, because the registry rejects overlapping `requires`/`enhances` declarations. Optional capabilities are expressed through the consumed ports instead.

## Static composition

`@skeletonstructure/app-composition` owns the checked-in M8 wiring:

- `createM8Composition()` builds each module, checks enabled ids, and calls `assertSinglePriceResolver()` **before** registry activation and before `createServer().listen()`.
- Multiple active `price-resolver@1` providers fail with `AMBIGUOUS_PRICE_RESOLVER`; the error names every conflicting provider and the configured application name.
- `additionalModules` lets an application register its own static provider so ambiguity can be detected without turning the framework into a plugin system.
- Routes are filtered to those declared in the activation report, so disabled modules register no HTTP surface.
- `runM8Migrations()` applies M1–M8 migrations in dependency order.
- `scripts/start-server.mjs` and `pnpm start` use this composition; `pnpm skeleton db migrate` and `pnpm db:migrate` use the same migration runner.

## HTTP surface

All routes are under `/v1` and use the standard success/error envelope.

| Method   | Route                         | Permission                      | Notes                                       |
| -------- | ----------------------------- | ------------------------------- | ------------------------------------------- |
| `GET`    | `/catalog/items`              | `catalog:read` (or public read) | `status`, `limit`, `cursor`, `expand`       |
| `GET`    | `/catalog/items/{id}`         | `catalog:read` (or public read) | `expand`                                    |
| `POST`   | `/catalog/items`              | `catalog:write`                 | base catalog fields only                    |
| `PATCH`  | `/catalog/items/{id}`         | `catalog:write`                 | partial update                              |
| `DELETE` | `/catalog/items/{id}`         | `catalog:write`                 | archives; status becomes `archived`         |
| `GET`    | `/catalog/items/{id}/product` | `catalog:read` (or public read) | product extension details                   |
| `PATCH`  | `/catalog/items/{id}/product` | `products:write`                | upsert; catalog item must exist             |
| `GET`    | `/inventory/items/{itemId}`   | `inventory:read`                | quantity and reserved units                 |
| `PATCH`  | `/inventory/items/{itemId}`   | `inventory:write`               | set stock for a catalog item                |
| `POST`   | `/orders`                     | `orders:create`                 | `Idempotency-Key` header required by config |
| `GET`    | `/orders/{id}`                | `orders:read`                   | owner only unless `orders:read:any`         |
| `GET`    | `/orders`                     | `orders:read`                   | `limit`, `cursor`; owner only               |

`?expand=<kind>` accepts only registered expansion kinds. An unknown kind returns `400 VALIDATION_ERROR` with `query.expand` in the details. With `products` enabled, `expand=product` adds a typed `details.product` object.

## Schema and migrations

Each package owns its Drizzle schema and generated SQL:

- `catalog_items`: unique slug, active/archived status, timestamps, and a status/created-at index.
- `commerce_products`: `catalog_item_id` primary key and foreign key to `catalog_items`, unique SKU, non-negative price, uppercase currency, optional weight and shipping class.
- `inventory_items`: `catalog_item_id` primary key and foreign key to `catalog_items`, quantity, non-negative reserved count, timestamps.
- `orders_orders`: `buyer_kind` constrained to `user`, `status` constrained to `confirmed`, idempotency fields, total amount, currency, unique `(buyer_ref, idempotency_key)`, and a buyer/history index.
- `orders_order_items`: immutable name, unit amount, currency, extension kind, details schema version, details JSON, quantity, and catalog item reference with `ON DELETE RESTRICT`.
- `orders_idempotency`: `(buyer_ref, idempotency_key)` primary key with `pending`/`completed` status, request hash, and resulting order id.

Migration order is `auth`/`users` → `catalog` → `products` → `inventory` → `orders`. No extension table may outlive its catalog item, and no order line may silently change when a catalog or product is edited later.

## Order behavior

- `orders.create` validates the canonical request and idempotency key before any write.
- With `price-resolver@1` enabled, all amounts and currencies come from the server; client-supplied `unitAmount` or `currency` is rejected.
- Each line stores `name`, `unitAmount`, `currency`, `extensionKind`, `detailsSchemaVersion`, and a JSON `details` snapshot. `products` uses `PRODUCT_EXTENSION_KIND = 'product'` and `PRODUCT_DETAILS_SCHEMA_VERSION = 1`.
- Duplicate idempotency keys with the same canonical payload return the original order. The same key with a different payload returns `409 IDEMPOTENCY_CONFLICT`. Database constraints and transactional conflict handling cover concurrent requests.
- Buyers are resolved only through `BuyerContextPort`. In v0.1 `currentBuyer()` returns a `user`; guest refs are rejected at the service and database boundaries.
- A non-owner receives `403 FORBIDDEN` unless the principal has `orders:read:any`.
- When `inventory` is disabled or not enabled in configuration, order creation performs no stock check. When enabled with `allowNegativeStock=false`, reservation occurs inside the order transaction and oversell is rejected.
- Reserved stock remains reserved after confirmation; cancellation, refunds, and automatic release are outside M8.

## Cursor pagination

`catalog` list and `orders` list accept opaque, base64url `limit`/`cursor` pagination. The response `meta.nextCursor` is optional. Core exposes only the generic `CursorPage<T>`, `pageResult()`, and `isCursorPage()` helpers; no module-specific pagination types were added to core.

## SDK

`@skeletonstructure/sdk` now exposes `catalog`, `products`, `inventory`, and `orders` namespaces in addition to `config`, `auth`, and `users`:

- `products.getAll()`/`getById()` force `expand=product` and narrow `details.product` types.
- `orders.create()` accepts `CreateOrderOptions.idempotencyKey` and sends it as `Idempotency-Key`.
- `catalog.getAll()`/`getById()` accept typed list/expand options.
- All public operation types are generated from the committed OpenAPI artifact; client helpers remain hand-written and browser-only.
- Both frontend examples now demonstrate catalog browsing and order creation through the SDK.

## Verification

Each of the four module packages has unit, real-PostgreSQL integration, and contract tests. The application-composition package covers resolver ambiguity and full-stack order flows, including concurrent idempotency and oversell. Deterministic checks are:

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm lint
pnpm test
pnpm test:contract
pnpm sdk:check
pnpm openapi:check
pnpm config:docs
```

## Limitations

M8 itself does not implement payments, guest checkout, Redis-backed rate limiting, real email providers, admin dashboards, multi-tenancy, restaurant modules, demonstrations, or M10 release work. M9a builds an app-local e-commerce demonstration on these packages without changing them; see [`m9.md`](./m9.md). Stock release is available as an inventory port method but is not tied to an order cancellation flow.
